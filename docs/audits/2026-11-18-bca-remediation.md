## Approved rolling submission-date policy (supersedes D+2 blocking below)

- At each preparation/dispatch use the current Vietnam calendar day, never a fixed date or login date. Preserve valid today/yesterday arrival values; clamp older arrival days to yesterday, retaining the time.
- For the outbound declaration only, raise expected departure to at least yesterday and the normalized arrival timestamp; raise foreign residence validity to at least today and the normalized arrival timestamp. Missing/malformed fields and future arrival remain validation failures.
- Never update PMS check-in/check-out dates or draft dates to these rounded values. Persist the actual outbound payload as the attempt snapshot. UNKNOWN reconciliation must match that snapshot's arrival day on the same facility, while local display retains actual dates.
- Safe unsent/failed active stays within the bounded 30-day queue may be prepared again on subsequent scheduled runs. UNKNOWN is not automatically resent from empty provider reads; SUBMITTED and CANCELLED remain excluded. A midnight boundary invalidating a claimed wire snapshot requires fresh preparation, not silent mutation of that claim.
- No browser/UI testing or live BCA calls are authorized by this source-change request.
- Confirmed provider rejection with locally valid data can retry on the next Vietnam day even if its normalized wire payload is unchanged. Same-day unchanged business rejection remains suppressed; invalid local data still requires correction.

## Latest Approved Policy Overrides (2026-11-18 Re-Review)

The following user-approved policies supersede earlier same-day-only and prepare-only migration assumptions in this register and in `.hermes/plans/2026-11-18_035617-bca-same-day-catch-up-and-soft-disconnect.md`:

1. **CURRENT DATE POLICY (Replaces same-day-only arrival restriction at submission/retry/recovery)**:
   - At every actual initial submit, retry, catch-up, and initial-recovery dispatch in `Asia/Ho_Chi_Minh`, validate against an injectable/pure current Vietnam date context:
     - `ngayDenCsltStr` calendar day MUST be **current Vietnam day (`today`) or `yesterday` (`today - 1 day`)**.
     - `ngayDiDuKienStr` calendar day MUST be **`>= yesterday`** (and `ngayDiDuKienStr >= ngayDenCsltStr`).
     - `thoiHanTamTruStr` (when applicable for `FOREIGN`) calendar day MUST be **`>= current Vietnam day (`today`)`** (and `>= ngayDenCsltStr`).
   - Preserve relative ordering, calendar validity, and active in-house stay status (`ACTIVE`, `CHECKED_IN`, `CHECKOUT_PENDING` with `checkedOutAt === null`).
   - Implement one reusable submission-time validator (`validateKbttSubmissionDates`) shared across immediate check-in/submit, scheduled sweeps (`12:00` / `21:00`), `10`-minute catch-up, and `KbttStaySyncService` initial/recovery routes.
   - Draft save (`saveDraft`) remains possible for incomplete/historical records, while dispatch fails locally with precise actionable field messages before calling BCA. Recalculate immediately before dispatch (including after midnight or slow operations). Never hardcode `2026-11-18`, UTC day, or login date.
2. **RETAIN ALL FAILED WORK & CROSS-DAY (`D+1` / `D+2`) SCHEDULING**:
   - Every failed record is retained for later handling, including across calendar days; never drop it or label retry safe regardless of cause.
   - Fixed `12:00`/`21:00` Vietnam sweeps and strictly future `10`-minute catch-up boundaries remain (`21:03 -> 21:10`; `21:10:00 -> 21:20`; recovery after `21:10` -> `21:20`).
   - At `23:55` Vietnam time, the next `10`-minute boundary (`00:00` next calendar day) is **allowed** so a guest who actually arrived on day `D` can retry on day `D+1` using their actual arrival date `D` (`yesterday` relative to `D+1`) if their payload and active stay remain valid at actual dispatch time.
   - By day `D+2`, arrival day `D` is outside the `[yesterday, today]` BCA window and fails local submission-time validation as needing manual handling (`OUT_OF_DATE_WINDOW` / `PRIOR_DAY_MANUAL_REQUIRED`) without fabricating arrival dates or auto-extending departure/residence validity.
3. **DAILY AUTHORITATIVE QUERY & 30-DAY BOUNDED HISTORY POLICY**:
   - Query authoritative pending/actionable cohorts directly in PostgreSQL by `(hotelId, active stay status, arrival day window / actionable declaration status, cursor)` with supporting indexes. Never scan the first 1,000/5,000 active guests in application memory to infer whether pending work exists.
   - When widening BCA history reads (`ls-khai-bao`), query only days with useful pending work, day-by-day within at most a rolling `30`-calendar-day window (`typeDate: 2`, `dateFrom = day`, `dateTo = day`), coalesced/reused per `(facility, generation, kind, day)` with strict page/request/row/time budgets. Budget exhaustion, changing totals, or partial reads are `INCOMPLETE` (inconclusive), never `NOT_FOUND`.
4. **CRITICAL `UNKNOWN` SAFETY (No Automatic Negative-Proof Resend)**:
   - Never convert an `UNKNOWN` declaration to `FAILED` or schedule an automatic resend based on an empty (`NOT_FOUND`) resident/history read (which races with in-flight/deferred POSTs or eventual provider listing and causes duplicate submissions).
   - Fence active dispatches durably via `KbttDeliveryLease` / `claimToken` / `attemptedAt` + `submittedConnectionCiphertext` across processes.
   - Only positive scoped matching acceptance (`MATCHED` with `bcaRecordId` on the same `csltId`) settles `UNKNOWN -> SUBMITTED`. In the absence of provider-supported transaction/idempotency nonacceptance proof, unmatched `UNKNOWN` records remain `UNKNOWN` (`RECONCILIATION_REQUIRED`) for explicit operator review after the in-flight lease settles.
5. **FACILITY & GENERATION FENCING ACROSS ALL DISPATCHES & RESULTS**:
   - `KbttRepository.findConflictingFacilityConnections` must not swallow DB errors into `[]`; DB errors must fail closed (`kbttUnavailable()`) and block dispatch.
   - Exclusive facility ownership and connection generation (`ciphertext` + `csltId` + active session token) must be enforced across **all** provider dispatches (`initial`, `scheduled`, `extend`, `checkout`, `recover`), rechecked immediately before the provider call after every `await`ed precondition, and fenced on post-provider result persistence so a late `401`/failure or cross-facility response from an older generation cannot overwrite a newer login or mark a different facility as accepted.
6. **NON-BLOCKING CONNECTION & TOGGLE REQUESTS**:
   - `connect`, `check`, `updateAutoSubmitEnabled`, and `updateAutoSubmitConfig` must persist state, register durable work, and return promptly without awaiting multi-second background `UNKNOWN` reconciliation.
7. **LOCAL DATABASE MIGRATION APPLICATION AUTHORIZED**:
   - Writing and applying the necessary additive schema/index/attempt-generation migration(s) to the verified local PostgreSQL database (`localhost:5432/vietsage_auth`) is explicitly authorized and required in this turn after pre-check and writer freeze.
